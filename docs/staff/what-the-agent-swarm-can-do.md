# What the agent swarm can do

Use this guide when you want an AI teammate to help change a page, fix a broken campaign link, improve how you show up in search, translate content, or clean up site quality — while **you keep final say**. The public site only changes when someone **approves edits** or **publishes a draft**.

Authors (Copy, SEO, Images, and so on) draft and file proposals. An **Approver** or **Publisher** is the one who publishes. The person who wrote the proposal should not be the one who approves it.

If your account instead has **direct edit** permission (change live or draft pages without an Approver inbox), see [What you can edit directly](what-you-can-edit-directly.md).

## Quick glossary

| Word you may see | What it means here |
|---|---|
| **Draft / test version** | A private copy of a page visitors do not see yet |
| **Publish the draft (Promote)** | Replace the live page with that draft |
| **Approve (Apply)** | Make the proposed edits real (live or on a draft) |
| **Greenlight (Accept)** | Say yes to an *idea* — the public page is still unchanged |
| **Needs fixes before approval** | Reviewer pause until the proposal is corrected |
| **Pick up** | “I’m working on this” issue or proposal |
| **Language version** | English, Spanish, and so on |
| **Shared template** | One layout reused by many pages of the same type |
| **Journey tags** | Product, audience, and stage labels for funnels |
| **Global Health** | Automated quality checklist for pages |
| **Runtime issues** | Log of broken links people (and bots) actually hit |

Where in the CMS: **Proposals**, and **Diagnostics** (Global, Runtime issues, Leads, SEO, GEO, Funnel).

### Hard truths (read once)

- **Filing a proposal does not change the live site.** Someone must **approve** edits `(Apply)` or **publish a draft** `(Promote)`.
- **Greenlighting an idea is not publishing.** `(Accept)` locks the brief and target page. A follow-up edits proposal still has to be approved — often with a redirect.
- **Drafts are safer than editing live.** Specialists usually work on private drafts. Publishing needs an Approver or Publisher — not the author.
- **Someone else must approve.** The author of a proposal should not be the one who clicks Apply.

### Does the public site change?

| What happened | Public site |
|---|---|
| Idea greenlit `(Accept)` | Unchanged |
| Edits approved `(Apply)` on live | Updated |
| Edits approved onto a draft only | Unchanged (draft updated) |
| Notes closed | Unchanged |
| Draft published `(Promote)` | Updated |

### Who usually does this (roster)

| Who to ask | Official name | What they’re for |
|---|---|---|
| **Planner** | Swarm Orchestrator | Plans, inspects, reads metrics, files proposals. Does not rewrite pages or approve. |
| **Copy** | Copy Editor | Body copy and drafts. Files proposals. Does not approve or publish. |
| **SEO** | SEO Specialist | Titles, descriptions, search fields, topic groups. Files proposals. Does not approve or publish. |
| **Page structure** | Layout Editor | Sections and shared templates. Files proposals. Does not approve or publish. |
| **Translator** | Translator | Other language versions. Files proposals. Does not approve or publish. |
| **Images** | Media Editor | Gallery and images on pages. Files proposals. Does not approve or publish. |
| **Approver** | Proposal Reviewer | Approves, rejects, greenlights, closes, asks for fixes. Does not create proposals or rewrite pages. |
| **Publisher** | Publisher | Publishes drafts, search checks around publish, full proposal lifecycle. |

## Start here by job

**Content marketer / editor** — Content chapters + Proposals. Prefer drafts. Let an Approver publish. Check Global Health after big publishes.

**SEO** — SEO chapter, Diagnostics → Global + SEO, Analytics. Use Proposals for titles and internal links.

**Paid / PPC** — Paid chapter, Runtime issues, Redirects. The swarm does not touch the ad account. Time Publisher with spend.

**Ecommerce / funnel** — Offers + conversion chapters + Funnel diagnostics. Sell flags stay human. Be strict on proof and numbers.

**Ops / webmaster** — Diagnostics (Global + Runtime), Redirects, Coordination. You own ignore/remove/test-link, holds, and bulk cleanups.

**Manager of the swarm** — Coordination + Proposals triage. Planner plans; Approver/Publisher stays separate from authors.

## 1. Content and storytelling

### Rewrite page copy without changing layout

**Situation:** A program or landing needs clearer headlines or body text. Layout stays the same.

**Agent can…** Read the live page, draft better copy on a private draft, or file an **edits** proposal for text only — with why it helps.

**What you approve:** Tone and facts. Approve `(Apply)` or publish the draft `(Promote)`. Reject or ask for fixes if claims are wrong.

**Who usually does this:** Copy. Approver or Publisher publishes.

---

### Add, remove, or reorder sections

**Situation:** Add a testimonial, drop a weak block, or move the CTA higher.

**Agent can…** Draft or propose section changes. Warn if a shared template is involved (many pages could change).

**What you approve:** Brand fit. Be careful with shared templates. Approve or publish when ready.

**Who usually does this:** Page structure. Approver or Publisher publishes.

---

### Create a new public page (blog post, landing, etc.)

**Situation:** Marketing wants a new URL for a campaign or topic.

**Agent can…** Check for duplicates, file an **idea** (brief + why + product/audience), then after greenlight file **edits** that build the page. Specialists do not quietly publish live pages alone.

**What you approve:** Greenlight or park the idea `(Accept)` / close. Then approve the follow-up edits. Park thin ideas.

**Who usually does this:** Planner or Copy for the idea; Page structure/Copy to build; Approver or Publisher to greenlight and approve.

---

### Try a private draft before replacing live

**Situation:** You want to test new copy or layout without visitors seeing it yet.

**Agent can…** Create a private draft, edit it, later propose publishing it over live. Live search title/description stay until you change them on purpose after publish.

**What you approve:** When to end the test and publish `(Promote)`. Confirm if asked about ending an experiment or recent edits on the page.

**Who usually does this:** Copy or Page structure for the draft; Publisher to publish.

---

### Translate a page into another language

**Situation:** An English page should also exist in Spanish (or another language).

**Agent can…** Write the translation on a private draft for that language, then propose publishing when ready. It will not silently overwrite other languages you did not ask for.

**What you approve:** Translation quality. Approve/publish per language. Expect separate work for each language.

**Who usually does this:** Translator. Publisher or Approver publishes.

---

### Use or leave a shared page template

**Situation:** A page needs a one-off layout — or should return to the shared template for its type.

**Agent can…** Propose leaving or rejoining the shared template and explain which pages share it.

**What you approve:** How widely the change spreads. Treat as high-care review.

**Who usually does this:** Page structure. Approver or Publisher with clear confirmation.

---

### Maintain FAQs and similar content lists

**Situation:** FAQs or reusable rows live in content lists (not always full pages).

**Agent can…** List and update those rows; refresh search over that list when needed.

**What you approve:** Accuracy and deletes. Know how your site ships these lists (it may differ from a normal page publish).

**Who usually does this:** Copy; Planner to inventory and propose.

## 2. SEO and discoverability

### Improve title and description for search results

**Situation:** The Google snippet underperforms (weak clicks or a vague title).

**Agent can…** Compare with related pages, draft a better title/description, file an edits proposal, and check recent edits so it does not overwrite a mid-campaign change.

**What you approve:** Brand voice and claims. Approve `(Apply)`. Watch real Search Console results — research is not the same as measured clicks.

**Who usually does this:** SEO. Approver or Publisher publishes.

---

### Fix missing rich-result info for Google

**Situation:** Quality checks show incomplete “extra info Google uses for rich results” on a page type.

**Agent can…** Inspect the page, propose fixes, and re-check quality after.

**What you approve:** Targeted fixes on selling pages vs bulk “fix everything.” Prefer targeted.

**Who usually does this:** SEO. Publisher re-checks around publish.

---

### Work a topic group (main page + related articles)

**Situation:** You own a topic (e.g. full-stack bootcamp) with a main page and related posts. Some articles are thin; some miss links.

**Agent can…** Show weak or orphan pages, propose internal links and copy, and use real organic traffic to prioritize.

**What you approve:** What belongs in the group. Approve link/copy proposals. Do not greenlight new URLs that only dilute the main page without demand.

**Who usually does this:** SEO (+ Copy for in-body links). Approver approves.

---

### Keyword research vs real traffic

**Situation:** You need ideas for what to write, plus honesty about what already gets clicks.

**Agent can…** Run keyword/competitor research (may use paid research budget when your site asks you to confirm), and separately read **measured** organic traffic. Must not invent click numbers.

**What you approve:** Research budget when asked. Business priority. Research does not auto-rewrite page SEO — someone still proposes those edits.

**Who usually does this:** SEO or Planner for research; SEO for the edits proposal.

---

### Language URL and slug conflicts

**Situation:** Two language versions collide on a URL, or a market needs a different URL shape.

**Agent can…** Surface this in quality checks, propose URL and search-title fixes, and propose redirects so old paths keep working.

**What you approve:** Final URL strategy per market. Approve redirects carefully so campaigns and bookmarks survive.

**Who usually does this:** SEO (+ Page structure if layout is involved). Publisher/Approver approves.

---

## 3. GEO and brand answers

### Triage brand / AI-answer views

**Situation:** You use Diagnostics → GEO to see how the brand shows up in answer-style surfaces.

**Agent can…** Improve the pages those views summarize: clearer facts, consistent product names, rich-result info, trustworthy copy. File proposals when live selling pages change.

**What you approve:** What “good enough” means for brand. The swarm does not replace brand-safety judgment.

**Who usually does this:** SEO and Copy; Planner to prioritize from Diagnostics. Approver for live changes.

---

### Keep product and audience naming consistent

**Situation:** Inconsistent names (“bootcamp” vs “course” vs wrong product) confuse journeys and answer surfaces.

**Agent can…** Audit journey-tagged pages and propose consistent naming and stage tags.

**What you approve:** Official product vocabulary. Approve journey-tag edits when they change how journeys are reported.

**Who usually does this:** SEO or Copy; Publisher when many journey pages publish together.

## 4. Ecommerce and offers

### Refresh offer copy and who it’s for

**Situation:** A product’s public story (audience, outcomes) is stale.

**Agent can…** Read the product and journey pages, draft copy updates, and propose product details (with confirmation).

**What you approve:** Whether claims are true. **Whether something is for sale / actively selling** stays a human Store decision — agents cannot flip those flags.

**Who usually does this:** Copy + Page structure; Planner to inventory. Notes or staff for sell flags.

---

### Complete or repair a product journey

**Situation:** A product should have awareness → consideration → conversion pages. Some stages are missing or mis-tagged.

**Agent can…** Map the journey, show gaps, propose journey tags, and summarize funnel analytics when available.

**What you approve:** Which pages sit in which stage. Approve tag proposals. Analytics inform priority; they do not auto-create pages.

**Who usually does this:** Planner to map; SEO or Copy for tags/copy; Approver approves.

---

### Selling pages with numbers and proof

**Situation:** A selling page needs outcomes, pricing cues, or proof — high risk if invented.

**Agent can…** Draft edits and mark them as selling-page / figures work so review is stricter. Prefer sourced numbers.

**What you approve:** Every number and claim. Ask for fixes or reject invented cards and unsourced “best of” lists.

**Who usually does this:** Copy drafts; Approver is strict; Publisher publishes.

## 5. Marketing and conversion

### Fix lead form and CTA tracking names

**Situation:** Diagnostics → Leads shows missing conversion names or tags that do not match your tracking setup.

**Agent can…** Inspect forms/CTAs, propose correct tracking names/tags, and re-check quality after.

**What you approve:** Canonical names for GTM/ads. Approve carefully — wrong names break reporting even if the form works.

**Who usually does this:** Page structure or Copy; Approver approves. Marketing ops owns the naming convention.

---

### Tag pages for funnel reporting

**Situation:** Pages need product, audience, and stage tags so Funnel diagnostics and analytics make sense.

**Agent can…** Propose journey-tag updates (often shared across language versions for that page’s common settings).

**What you approve:** Your naming rules for stages. Mis-tags poison dashboards.

**Who usually does this:** SEO or Planner proposes; Approver approves.

---

### Hand off a side issue without blocking a good edit

**Situation:** While reviewing a title change, you notice a broken CTA elsewhere on the same page.

**Agent can…** Keep the original proposal focused and file a separate **notes** item so the CTA is tracked without blocking the title approval.

**What you approve:** Must-fix-before-approve vs fix-later note. Close notes when acknowledged.

**Who usually does this:** Approver decides; authors follow up with edits.

---

## 6. Paid / PPC and campaigns

### Spin up a campaign landing draft

**Situation:** Paid needs a landing URL for a new ad set next week.

**Agent can…** Draft the landing on a private draft, or idea → greenlight → edits that build the page. Align product/audience and tracking names with your brief.

**What you approve:** When it goes live relative to spend. The swarm does **not** create campaigns, change bids, or pause ads — that stays in the ad platforms.

**Who usually does this:** Copy + Page structure (+ SEO for search titles). Publisher times publish with media.

---

### Clean up after a campaign ends (dead URLs and tracking tags)

**Situation:** Ads still send traffic to a URL that 404s, or campaign-tagged paths clutter Runtime issues.

**Agent can…** Read the broken-link log (when allowed), show path, hits, sources, and campaign tags, and file a **broken URL** idea with that proof. Later propose a redirect — or a new page if traffic justifies it.

**What you approve:** Test the link, add a redirect, or ignore junk paths. Close low-traffic broken URLs instead of inventing pages. Pause ads yourself in the ad platform.

**Who usually does this:** Planner or Approver for evidence + idea; Approver/Publisher for greenlight and redirect approval. Paid media owner for the ad account.

---

### Keep organic tests and ads from fighting on one URL

**Situation:** SEO title tests and paid creative share a URL; one almost overwrites the other.

**Agent can…** Check recent activity before proposing title changes and warn when the page was just edited.

**What you approve:** Recent-activity warnings. Coordinate SEO and paid calendars.

**Who usually does this:** SEO; Approver confirms before approving.

## 7. Media and creative

### Find or register an image for a page

**Situation:** A section needs a hero or card image from the gallery (or a public URL to import).

**Agent can…** Search the gallery, look up or import from a public URL, and attach it on a draft or via proposal.

**What you approve:** Rights, brand fit, mobile crop. Reject off-brand imports.

**Who usually does this:** Images. Approver if the change is for live.

---

### Fix missing or poorly optimized images

**Situation:** Global Health shows missing, untagged, or heavy images.

**Agent can…** Pick up the quality issue, fix page references, and mark done with a short why. Bulk gallery cleanups may still need staff tools.

**What you approve:** Run bulk cleanups from Diagnostics when the problem is gallery-wide. Dismiss false positives.

**Who usually does this:** Images for page-level fixes; staff ops for gallery-wide cleanups.

---

### Refresh the social share preview image

**Situation:** Slack or LinkedIn still shows an old preview after a redesign.

**Agent can…** Queue regeneration of the page’s social share preview.

**What you approve:** Confirm the new creative first. Social networks may need their own refresh.

**Who usually does this:** Images.

## 8. Site quality (Diagnostics)

*Path 2 — If you own the health board.*

Diagnostics has two layers people often mix up:

1. **Global Health** — automated checks of your pages (search, integrity, images, forms, components, and more).
2. **Runtime issues** — live log of **public 404s** (broken links people and bots hit).

**Leads**, **SEO**, **GEO**, and **Funnel** tabs are priority boards. Agents improve the underlying content; you still interpret the boards.

Where in the CMS: **Diagnostics** → Global / Runtime issues / Leads / SEO / GEO / Funnel.

---

### Refresh and understand Global Health for a page

**Situation:** A page looks wrong in search, fails a pre-publish checklist, or the on-page error panel shows problems.

**Agent can…** Re-run checks for one page, list open issues, pick one up, fix it on draft or live (when allowed), and mark done. For many pages, it starts a job you can watch.

**What you approve:** Site-wide refresh, dismissals, CSV export, bulk cleanups. Use **Solve with AI** to seed a specialist session. Reopen if “done” was premature.

**Who usually does this:** Matches the issue (SEO / Images / Page structure). Publisher often re-checks around publish.

---

### Work an open quality issue to done

**Situation:** Global Health lists an error or warning (missing required field, redirect conflict, empty language version, unknown section type, and so on).

**Agent can…** Pick up the issue, fix it, re-check, and complete or reopen with a short report. Some engineering-only issues stay with engineering.

**What you approve:** Priority (errors vs warnings). Dismiss noise. Resolve redirect conflicts in the dedicated UI when that issue appears.

**Who usually does this:** By category — SEO / Copy / Page structure / Images. Planner may triage without fixing.

---

### Read the Runtime issues (broken link) log

**Situation:** Something still sends traffic to a dead path — old ads, Google results, internal links, or bots.

**Agent can…** Read the log with filters (path, language, device, source like search / social / internal, last 7 or 30 days). Summarize hits, first/last seen, sample referrer, and campaign tags. Use that proof in a **broken URL** idea (only roles that can read the log — others must not invent hit counts).

**What you approve:** **Test the link**, **add a redirect**, **ignore** path rules, **remove** rows from the list, reset the log, pull a production snapshot, or stop logging scrapers. Agents cannot ignore, remove, or test-link via the swarm — that is staff CMS work.

**Who usually does this:** Planner or Approver to read and file ideas; staff ops for ignore/remove; Approver/Publisher for greenlight + later redirect approval.

---

### Decide what a broken URL deserves

**Situation:** A 404 has real traffic. You need a clear decision.

**Agent can…** File a broken-URL **idea** with proof pasted in (path, counts, sources, referrer, campaign tags or “none”). Say whether a live page already answers that address **and** matches product + audience.

**What you approve:**

- Live page fits → **greenlight** `(Accept)` that existing page; follow-up edits = **redirect only**. Public site still unchanged until the follow-up is approved.
- No match, high traffic → **greenlight** a **new** page URL (not the broken path itself); follow-up builds the page then adds the redirect.
- No match, low traffic → **close** (do not invent a page).
- Thin or mismatched proof → **ask for fixes** before greenlight.

**Who usually does this:** Planner/Approver for the idea; Approver or Publisher for greenlight and follow-up approval.

---

### Use SEO / Funnel / Leads tabs as priority boards

**Situation:** You plan a sprint from Diagnostics overview tabs, not from one page editor.

**Agent can…** Turn board findings into proposals (orphans → link edits; funnel gaps → journey tags; lead mismatches → CTA fixes).

**What you approve:** Sprint priority. Boards do not auto-file proposals.

**Who usually does this:** Planner for triage; specialists for each fix type.

## 9. Proposals and review

*Path 2 — If you own the proposal inbox.*

Proposals are the shared inbox for change. Live content does not move when a proposal is filed. Where in the CMS: **Proposals**.

### Three kinds of proposal

| Kind | What it is | How it finishes | Public site |
|---|---|---|---|
| **Edits** | Concrete changes, publish a draft, or create a new allowed page | **Approve** `(Apply)` or **Reject** | Updated if Apply is on live; else draft only / unchanged on reject |
| **Idea** | Brief to greenlight a new page or strategy | **Greenlight** `(Accept)` or **Close** | Unchanged |
| **Notes** | Handoff / reminder with no field changes | **Close** | Unchanged |

---

### File work for someone else to review

**Situation:** A specialist finished research and wants a safe path to live.

**Agent can…** File edits / idea / notes with a plain-English summary (intent and why). Tag the review type when known (search snippet, internal links, journey tags, translation, selling figures, new page, publish draft, broken URL, and so on). Link related pages. For follow-ups after an idea was greenlit, connect to that idea.

**What you approve:** Everything in the queue. Put a proposal **on hold for a manager** if it is sensitive — that freezes agent updates until you release it.

**Who usually does this:** Any create-capable specialist or Planner. A different Approver/Publisher approves.

---

### Triage the open queue

**Situation:** Many open proposals; you need what needs attention first.

**Agent can…** List proposals with stats, filter by attention (on hold, waiting for re-review, no feedback, needs fixes), stalled greenlit ideas, needs-review edits, who filed, and text search. Open one for full context.

**What you approve:** Same filters and KPI strip in Proposals. Use badges (risk level, draft vs live mode, needs-fixes) to prioritize.

**Who usually does this:** Approver or Publisher to decide; Planner for read-only triage and filing.

---

### Pick up, polish, or withdraw before review

**Situation:** Reviewer asked for fixes; the author needs to correct the proposal.

**Agent can…** Pick up, revise the listed changes, resolve “needs fixes,” retag review type, attach a private draft, turn off auto-retry, or withdraw. Open “needs fixes” blocks Approve `(Apply)` and greenlight `(Accept)`.

**What you approve:** Staff can flip some flags (like don’t auto-retry) without the same pick-up steps. Hold / release hold is staff-only.

**Who usually does this:** Original author for polish; Approver for quality of the fix request.

---

### Approve an edits proposal

**Situation:** The changes look good; you want them on the site or on a named draft.

**Agent can…** (Approver/Publisher) Approve `(Apply)`: write fields on live, write onto a draft, publish a draft over live, or create a new page when the proposal says so. The whole proposal succeeds or is left partial — it does not quietly ship only some changes. May ask you to confirm (end an experiment, confirm new values, recent activity).

**What you approve:** Final yes. Preview draft-backed work first. If some pages succeed and others fail, you get a **partial** — remaining work stays in review.  
**Public site:** updated when you approve live changes `(Apply)` or publish a draft `(Promote)`; unchanged if only a draft was updated.

**Who usually does this:** Approver or Publisher only (not the author).

---

### Greenlight or park an idea

**Situation:** Someone pitched a new URL or a structural brief.

**Agent can…** Review opportunity vs harm: goal, evidence, fit, brand, and whether a mediocre page would tax the site. Greenlight with a next step and locked target, or close/park. Demand labels (anticipated demand, fast news, broken URL) need matching evidence.

**What you approve:** Same greenlight/close in the UI. **Greenlight ≠ live page.** Track stalled ideas (greenlit with no follow-up edits).  
**Public site:** unchanged.

**Who usually does this:** Approver or Publisher.

---

### Ask for fixes, reject, or note side problems

**Situation:** The proposed change is almost right — or completely wrong.

**Agent can…**

- **Ask for fixes** — proposed change is wrong or incomplete; blocks Approve `(Apply)` / greenlight `(Accept)` until resolved.
- **Side notes** — out-of-scope live defects; do **not** block Approve.
- **Reject** — rare, final (bad idea, not doable, policy, harmful, weaker duplicate, target missing). Needs a serious written reason.

**What you approve:** Prefer “needs fixes” for polishable work. Reject when the idea itself must die. Close notes when acknowledged.

**Who usually does this:** Approver.

---

### Broken URL path (Runtime → Idea → Approve)

**Situation:** Diagnostics → Runtime issues shows a hot 404; you want a clean redirect or new page.

1. **Evidence** — Agent (with log access) or you reads Runtime issues for that path.  
2. **Idea** — File broken-URL idea with proof in the summary.  
3. **Greenlight** `(Accept)` — Lock an existing matching page **or** a new URL (high traffic only) **or** close (low traffic). **Public site: unchanged.**  
4. **Follow-up edits** — Separate proposal: redirect only, or create page then redirect.  
5. **Approve** `(Apply)` — Now the site changes. Test the old path again in Runtime issues.

**Who usually does this:** Planner/Approver for steps 1–2; Approver/Publisher for 3–5; staff for test-link/ignore if the row is junk.

---

### Review types you’ll see (plain English)

| Label in the CMS | Everyday meaning |
|---|---|
| Search title / description | Snippet copy for search results |
| Internal links | Main page ↔ related article links |
| Journey tags | Product / audience / stage |
| Body copy | Normal wording changes |
| Selling figures | Numbers and proof on selling pages |
| New public content | Net-new URL / new page |
| Publish draft | Draft becomes live |
| Language translation | Another language ready to publish |
| Broken URL | 404 demand proof from Runtime issues |
| Idea opportunity vs harm | Is this worth it, or does it dilute the site? |
| Anticipated demand / fast news | Idea flavors (research or news timing) |

Empty labels on edits may be inferred from what the proposal changes (often body copy). Mixing selling-page work, brand-new pages, and unrelated fixes in one proposal is refused — split the work.

## 10. Redirects and URL hygiene

### Test where a path goes today

**Situation:** Before changing ads or sitemaps, you need to know which redirect wins and whether two rules conflict.

**Agent can…** Test a URL and report the winner and conflicts.

**What you approve:** Which rule should win. Fix conflicts in the redirects UI when Global Health flags them.

**Who usually does this:** SEO or Planner; staff for the conflict UI.

---

### Add or move a redirect

**Situation:** An old campaign URL must land on the new program page.

**Agent can…** Propose or ship a single redirect after testing (when allowed). Broken-URL follow-ups often ship the redirect when you **approve** the follow-up edits.

**What you approve:** Final redirect map. Prefer exact old paths so visitors are not bounced twice. **Ignore** on Runtime issues only hides log noise — it is not a redirect.

**Who usually does this:** SEO proposes; Publisher/Approver when it goes through Proposals; staff Runtime tab for quick add-from-row.

## 11. Analytics-informed work

### Prioritize from organic traffic

**Situation:** Limited editor time; you want pages with real impressions/clicks first.

**Agent can…** Read organic traffic for the site, paths, or topic groups, and turn winners/losers into proposal candidates.

**What you approve:** Business priority (a low-traffic strategic page can still win). Agents must not invent traffic numbers.

**Who usually does this:** Planner or SEO.

---

### Use named analytics reports (including journeys)

**Situation:** You want journey KPIs or a named analytics report to brief an agent.

**Agent can…** Pull the report, summarize where pages underperform, and propose content or journey-tag fixes.

**What you approve:** Whether metric movement is worth a live change. Reports never auto-approve edits.

**Who usually does this:** Planner for briefing; specialists for fixes; Approver for approval.

## 12. Coordination

### Plan a multi-step initiative without writing pages

**Situation:** “Improve the full-stack topic group this month” needs research, several edits, and a publish order.

**Agent can…** (Planner) Inspect content, metrics, and Diagnostics; file ideas and notes; hand off to Copy / SEO / Page structure / Images; never approve or rewrite live pages itself.

**What you approve:** Who reviews and in what order. Keep authors separate from Approvers.

**Who usually does this:** Planner plans; specialists execute; Approver / Publisher decide.

---

### Solve with AI from Diagnostics

**Situation:** You are on a Global Health row or page error and want a specialist session with the right context.

**Agent can…** Pick up the seeded brief (page + issues) and work the fix / propose loop.

**What you approve:** Starting Solve with AI, then reviewing whatever proposal or live fix results. You remain accountable for approval.

**Who usually does this:** Whatever the prompt selects (often SEO or Copy); Approver for publish.

### When agents are propose-only or a proposal is on hold

**Situation:** Security locked agents so they can only file proposals (not write pages), or a manager put a sensitive proposal on hold.

**Agent can…** Still file proposals (when allowed) but cannot approve them or write live/draft content. Held proposals freeze agent updates until staff releases the hold.

**What you approve:** Approve in Proposals yourself (or turn writing back on for a trusted Approver). Release the hold when safe.

**Who usually does this:** Authors propose; humans or Publisher/Approver with write access decide.

## What the swarm will not do today

- Change bids, budgets, or creatives inside Google Ads, Meta, or other ad platforms.
- Flip store “for sale” / “actively selling” flags (human Store or a notes process).
- Change the live site merely by **filing** a proposal or **greenlighting** an idea.
- Silently translate and publish every language when you edit one.
- Invent Search Console clicks, keyword volumes, or 404 hit counts.
- Ignore, remove, test-link, or reset Runtime 404 rows (staff CMS only).
- Pick up engineering-only quality issues meant for coding agents.
- Approve their own proposals when someone else must approve.
- Fix your chat app’s connection after a platform upgrade (reconnect when staff asks).
- Replace your brand, legal, and factual judgment on selling pages.
